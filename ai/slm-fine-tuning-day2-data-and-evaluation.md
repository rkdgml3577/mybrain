# SLM 파인튜닝 2일차 — 데이터 설계와 학습·평가 실행

2일차. 개념을 새로 쌓기보다 ① LoRA를 더 깊이 이해하고(QKV 위치·팔레트 비유), ② 실제로 학습·평가를 돌려 Base vs Fine-tuned를 확인. 관통하는 메시지는 **"성능을 결정하는 건 알고리즘이 아니라 데이터 설계"**.

## 핵심 개념

- **파인튜닝의 정의(재확인)** — 베이스 모델이 최초로 만들어진 상태 = 사전학습 모델(Pre-trained). 이후 용도에 맞춰 재학습하면 무조건 파인튜닝. 그 안에서 전체를 다시 학습하면 Full Fine-tuning, 원본을 동결하고 일부만 추가하면 PEFT.
- **LoRA = Low-Rank Adapter** — "Low-Rank"는 저용량이라는 뜻. 원본 파라미터를 동결하고, 목적에 필요한 소수 파라미터만 추가로 학습해 붙임.
- **Q·K·V** — 트랜스포머 어텐션의 Query·Key·Value. LoRA를 붙일 위치가 여기(주로 `q_proj`, `v_proj`).
- **데이터 설계(Data Design)** — 질문/정답 쌍을 어떻게 구성·균형·정리하느냐. 이번 과정에서 성능을 좌우하는 가장 중요한 요소.
- **평가 지표** — Keyword Score(핵심어 일치), Token F1(겹침 정도, 0~1), Hallucination(없는 규정을 지어내는지).
- **Foundation Model** — 언어를 넘어 음성·이미지까지 다루도록 발전한 원천 모델. 여러 원천을 다루면 Multimodal.
- **Vector DB / Embedding** — 자주 바뀌는 대량 지식을 벡터(방향값)로 변환해 저장. AI(기계)가 읽기 위한 형태.

## 도메인·배경 지식

- ⭐ **성능을 결정하는 건 데이터다 (이번 과정의 핵심 결론)**: 알고리즘·모델 자체로는 성능 차이가 크지 않음. 하이퍼파라미터 튜닝도 해봐야 아는 수준. 실제로 성능을 좌우하는 건 "질문/정답 쌍을 얼마나 균형 있게 구성해 학습 데이터를 만드느냐." 그래서 알고리즘을 파기보다, 현장 도메인을 잘 아는 사람이 데이터를 어떻게 설계하느냐가 관건. → 도메인 지식이 경쟁력인 이유.
- **우리가 있는 위치**: 프론티어 모델을 새로 사전학습하는 영역은 막대한 자원·컴퓨팅 격차가 필요해 국내 대학원·기업 R&D도 따라가기 어려움. 우리는 이미 나온 베이스 모델을 현장에 맞게 특화하는 실전 영역에 있음. 알고리즘 이해는 중요하지만 그게 승부처는 아님.
- **도구는 이미 공개돼 있다**: 트랜스포머 구조, PEFT, 학습 도구는 논문으로 다 공개됨. 누구나 같은 도구를 손에 쥠. 승부는 "도구를 붙이는 법"이 아니라 그 위에 무엇을 그리느냐(도메인 지식·데이터 구성).
- **왜 언어 모델이 생성형 AI의 시작인가**: 인류가 쌓아온 데이터 중 언어 데이터가 가장 많아서. 이후 음성·이미지까지 다루며 **Foundation Model → Physical AI(현실 세계로 나옴)**로 확산 예정. 이미지/UI 다루는 경험도 그때 부각됨.
- **DeepSeek 경고**: 오픈소스라고 무조건 안전한 게 아님. DeepSeek은 사용자 입력 정보를 특정 주소로 전송해 위험. 반면 Qwen은 다양한 각도의 검증을 거쳤고 안정적으로 쓰인 레퍼런스가 많아 권장. Llama도 오픈소스 생태계에서 검증 과정을 거침. → 모델은 검증된 것만 수용.

## 원리·메커니즘

- **왜 일부만 업데이트가 안 되나(재확인)**: 딥러닝은 뉴런처럼 자극(가중치)이 층을 타고 전파되는 구조라, 일부만 수정하려 해도 가중치가 전파되어 전체가 뭉개짐. 그래서 "일부만 수정"이 불가능 → 원본을 동결하고 어댑터를 얹는 LoRA로 우회.
- **LoRA = 팔레트 비유(핵심 직관)**: 벽화를 그릴 때 세상의 모든 색을 다 쓰는 게 아니라, 그 그림에 필요한 물감만 팔레트로 뽑아 씀. LoRA가 하는 게 이것 — 전체 파라미터(십수억)를 동결하고, 이 도메인 그림에 필요한 소수 파라미터(팔레트)만 뽑아 학습. 어제 코드에서 LoRA 붙이자마자 학습 대상 파라미터가 확 줄어든 게 이것.
- **LoRA는 "병렬"이 아니라 "병합"**: 원본 옆에 따로 떨어져 도는 게 아니라, 학습한 작은 보정값이 원본 가중치(W)와 합쳐짐. 원본 W는 안 건드린다는 뜻.
- **왜 붙이는 위치가 Q·V인가**: 어텐션은 "전체를 다 보고, 이 맥락에서 집중할 곳을 Query·Key·Value 조합으로 고르는" 알고리즘. LoRA는 이 중 어디에도 붙일 수 있지만, 예시에서는 Q·V 두 곳만 선택(빠르고 성능 예시를 보여주기 위해). 실전에서는 더 많은 위치에 붙이기도 함 → 시간·성능 트레이드오프, 선택의 문제.
- **다중 어댑터**: 언어 모델(LLM)에서는 어댑터를 여러 개 동시에 붙이지 않음 — 문체·규칙 도메인이 문장 단위로 충돌·간섭. 반면 **이미지 생성 모델(Stable Diffusion)**은 병렬 처리라 여러 LoRA를 겹쳐도 혼선이 적음. (모델 종류에 따라 다름)
- **같은 시드면 같은 파라미터?**: 같은 베이스·구성·시드면 이론적으론 동일 파라미터가 나와야 하지만, 실제로는 미세하게 달라 완전히 똑같긴 어려움.
- **SFT의 본질(중요)**: SFT는 모델의 지식을 바꾸는 게 아니라, "어떤 형식·태도로 답할지"를 예시로 각인시키는 과정. 그래서 데이터의 형식·일관성이 곧 결과.

## 실습·도구·코드

- **학습 데이터 설계 (dataset — 이번 세션의 하이라이트)**:
  - 형식: 대화형 `messages`(system/user/assistant), 질문/정답 쌍. 582개 레코드.
  - 가상의 Human AI Corporation 사내 규정 + 임의 정책 코드(AURORA·BLUE-7·LYNX·SOLAR 등) — 베이스 모델이 절대 모르는 것으로 설계해 학습 효과를 확인.
  - 시스템 프롬프트 원칙: 결론 먼저 → 절차를 순서대로, 예외와 함께 안내.
  - 설계에 녹인 것: 원천 규정을 같은 비율로 노출, 토픽별 노출 균형, 정답 없는 질문엔 "모른다"고 답하도록(Hallucination 방지), 데이터 간 일관성, 거절 샘플, 출처 추적성.
  - 핵심 교훈: 실무에선 사내 매뉴얼을 토대로 이런 질문/정답을 뽑고 JSON 포맷으로 구성하는 게 진짜 일. 도메인 이해 → 데이터 구조화가 성능을 만든다.
- **학습 실행 (`train_lora.py`)**:
  - Base 모델(Qwen2.5-1.5B)은 HuggingFace 캐시에 로컬 다운로드(상용 LLM처럼 API 키로 매번 호출하는 게 아니라, 내 로컬에 두고 씀). 경로 미지정 시 자동 캐시 관리 → 신경 안 써도 됨.
  - LoRA는 원본을 안 건드리므로 재학습해도 베이스를 다시 받을 필요 없음.
  - 메모리 설정: gradient accumulation 등(16GB Mac 기준). 학습 약 10분 소요.
  - 코드 읽는 법: `main` 함수부터 보기. main이 시작점이고, 그 앞의 함수·변수들은 main이 쓰기 위한 준비물. → 나중에 내 코드 만들 때도 이 틀 재사용.
  - 결과물: `models/hr-qwen-lora/`에 어댑터 생성 + `training_log.json`(loss/eval_loss 등) + `training_summary.json`.
- **평가 실행 (`evaluate_model.py`)**:
  - 같은 질문을 Base와 Fine-tuned에 각각 던져 답을 비교. main 구조는 동일.
  - 결과: 10문제 중 파인튜닝 9승·1무 → SFT가 의도한 방향으로 개선됨을 확인.
  - 지표: Keyword Score, Token F1(1=100%). 일부 저조하거나 출력이 깨진 건 모델이 작아서(1.5B).
  - ⚠️ 교수님 주의: "이렇게 쉽게 안 나옵니다." 데이터를 학습 목적에 맞게 일부러 맞춰놨기 때문에 잘 나온 것. 실전에선 데이터 구성이 그만큼 어려움.
- **RAG 데모 비교(오후 참고)**: SFT 단독 ≈ +10% 개선, SFT+RAG ≈ +50%. 단, 벡터 DB에 모든 정보가 있으면 Base+RAG가 Fine-tuned보다 높게 나오기도 함(검색이 다 잡아주니까). 데모 서버는 캐시 히트로 즉답, 새 질의는 ~10초(동시 접속 시 대기).

## 예시

- **팔레트/물감(LoRA)** — 벽화에 필요한 색만 뽑아 쓰는 것.
- **Human AI Corporation** — AURORA·BLUE-7·LYNX·SOLAR 등 가상 정책 코드로 "베이스가 모르는 것"을 학습.
- **Stable Diffusion 다중 LoRA** — 이미지 모델은 어댑터를 겹쳐도 혼선이 적음(LLM과 대비).
- **동시통역사** — 구글이 온디바이스 통번역을 오픈하면 범용 통번역 시장은 타격, 살길은 버티컬(전문 도메인).

## 헷갈리는 점·질문

- LoRA를 왜 Q·V에만? → 예시라서 2곳만. 실전엔 더 붙이기도 함(시간↔성능). Q·K·V가 어텐션의 그 QKV라는 걸 연결하면 이해됨.
- 같은 조건이면 같은 결과? → 이론상 yes, 실제론 미세하게 다름.
- "데이터가 성능을 결정한다" → 이번 과정에서 계속 나온 질문("결국 데이터가 중요한 거 아니냐")에 교수님이 "맞다, 그게 핵심"이라 답. 알고리즘보다 데이터 설계.
- SFT 결과가 왜 이렇게 잘 나왔나? → 데이터를 학습 목적에 맞게 맞춰놨기 때문. 실전은 안 이럼.
- Base+RAG가 Fine-tuned보다 좋을 수도 있는 이유? → 벡터 DB에 정보가 다 있으면 검색이 잡아줌 → 파인튜닝 vs RAG 역할 분담을 다시 생각하게 함.

## 한 줄 요약

> LoRA는 벽화에 필요한 물감만 뽑는 팔레트처럼 원본을 동결하고 소수 파라미터(Q·V)만 학습하는 것이며, 실제 성능을 가르는 건 알고리즘이 아니라 질문/정답 데이터를 어떻게 균형 있게 설계하느냐다 — 실습에서도 잘 맞춰둔 데이터 덕에 파인튜닝이 10문제 중 9승했다.
