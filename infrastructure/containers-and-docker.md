# 컨테이너와 Docker — VM 비교·이미지 레이어·볼륨·네트워크·레지스트리

컨테이너 과정. 왜 클라우드/컨테이너인가 → VM vs 컨테이너 → 이미지 레이어 구조 → 컨테이너 임시성과 볼륨(영속성) → 자원 제한 → 네트워크 → 레지스트리(push). 모레부터 Kubernetes로 이어짐.

## 핵심 개념

- **VM (Virtual Machine)** — 가상 소프트웨어(하이퍼바이저)로 하드웨어를 논리적으로 분리한 가상 머신. 각 VM은 개별 Guest OS를 가짐.
- **하이퍼바이저 (Hypervisor)** — 물리 자원(vCPU·메모리 등)을 VM별로 할당·분리해주는 가상화 소프트웨어.
- **컨테이너 (Container)** — Guest OS 없이, 호스트 OS 커널을 공유하며 앱을 격리 실행하는 단위. VM보다 가벼움.
- **이미지 (Image)** — 컨테이너를 만들기 위한 읽기 전용 템플릿. 레이어 구조.
- **레이어 (Layer)** — 이미지를 이루는 층. Dockerfile 명령어 한 줄 ≈ 레이어 한 장.
- **Dockerfile** — 이미지를 만드는 명세. FROM(베이스 이미지) → WORKDIR → COPY → ENTRYPOINT 등.
- **볼륨 (Volume)** — 컨테이너가 죽어도 데이터를 유지(영속성)하기 위한 저장소.
- **임시성 (Temporary)** — 컨테이너/Pod는 언제든 사라질 수 있는 임시 존재.
- **Pod** — Kubernetes에서 컨테이너를 감싸는 최소 관리 단위.
- **레지스트리 (Registry)** — 이미지를 저장·공유하는 저장소. Docker Hub, Harbor, AWS ECR 등.
- **CNI / CSI** — Kubernetes의 네트워크 인터페이스 / 스토리지 인터페이스.

## 도메인·배경 지식

- **왜 클라우드가 근본인가**: 데이터 사이언스·AI가 이렇게 발전한 근본 이유가 클라우드. "내가 원할 때 원하는 만큼 자원을 쓴다"는 게 대규모 학습·서비스를 가능케 함. 그런데 컴공·데이터사이언스 전공에서도 클라우드를 잘 안 가르쳐, 처음 접하는 사람이 대부분.
- **VM의 장점과 단점(동시에)**: 장점 — VM마다 OS를 자유롭게 선택(Windows / Linux(Ubuntu·RedHat) 등). 단점 — VM마다 Guest OS가 자원을 차지해 무거움. 이 Guest OS 부담을 없애려는 데서 컨테이너가 나옴.
- **왜 컨테이너/오케스트레이션인가**: 백엔드·프론트에서 만든 걸 인프라적으로 안정성·가용성·성능 있게 서빙하려고 컨테이너를 씀. 수많은 서비스 컨테이너를 유기적으로 관리하려 오케스트레이션 도구 Kubernetes를 배움. → 큰 앱 덩어리를 잘게 쪼개(MSA) 개별·빠른 배포를 하려는 흐름(예: 예전 통신사 백엔드는 매주 정해진 날 밤새 배포).
- **레지스트리 선택은 케바케(현업)**: 회사·사이트마다 다름. SKT는 사내 소스리포 + CI/CD 서버, AWS(→ ECR) 사용, 계열사는 Azure DevOps 사용 등 제각각. Harbor 장점 — 클러스터에 쉽게 설치·구성, 비용이 적게 듦(ECR은 용량 따라 비용이 꽤 나옴). 정답이 하나로 정해지지 않음.

## 원리·메커니즘

- **VM vs 컨테이너 구조**: VM = 하드웨어 → 호스트 OS → 하이퍼바이저 → (Guest OS + 앱) × N. 컨테이너 = 하드웨어 → 호스트 OS → 컨테이너 엔진 → (앱) × N, Guest OS 없음 → 가볍고 빠름.
- **이미지 레이어 구조**: Dockerfile의 명령어 한 줄 = 레이어 한 장. 여러 읽기 전용 레이어를 머지해 하나의 파일 시스템(`/`)처럼 보여줌. 베이스 이미지·WORKDIR는 거의 안 바뀌어 캐시 재사용, COPY로 코드가 바뀌면 그 레이어부터 새로 생성. 컨테이너는 맨 위에 **쓰기 가능 레이어(컨테이너마다 하나)**를 얹어 데이터를 씀 → 이미지 자체는 불변(읽기 전용).
- **컨테이너의 임시성 & IoC 연결**: 컨테이너/Pod는 임시적(temporary)이라 언제든 죽을 수 있음 — 스프링의 객체가 개발자 통제 밖에서 IoC 컨테이너에 의해 관리되는 것과 유사. 제어의 역전(Inversion of Control): 내가 통제하지 않고 컨테이너가 알아서 등록·실행. 컨테이너도 내가 통제 못 하니, 데이터를 지키려면 볼륨이 필요.
- **볼륨(영속성)**: 컨테이너가 죽어도 데이터가 사라지지 않도록 외부 저장소를 마운트. (컨테이너 임시성 문제의 해법)
- **자원 제한(request/limit)**: 컨테이너·Pod별로 CPU·메모리의 **최소(request)·최대(limit)**를 설정. 백엔드 힙 메모리의 min/max 설정과 같은 개념. 스토리지도 제한 가능.
- **컨테이너 네트워크**: 컨테이너 내부↔외부는 **가상 브리지(docker0)**와 호스트 물리 NIC 사이의 패킷을 **NAT(포트 포워딩)**로 연결. 예: 호스트 8080 요청 → 컨테이너 80으로 전달(터널링/매핑). 같은 브리지 안 컨테이너는 IP로 통신. Docker 네트워크 모드: bridge / host 등. Kubernetes는 Calico 등으로 오버레이 네트워크(CNI) 구성.

## 실습·도구·코드

- **DB 접속 3가지 경로**: ① 터미널 콘솔, ② VS Code(Database 확장 플러그인 설치 후 커넥션), ③ DBeaver 클라이언트 툴. 편한 걸로.
- **이미지 백업/추출**: `docker save`로 이미지를 tar로 추출(`-o linux.tar` 등). tar 압축은 보통 `tar cvf`, 해제는 `tar xvf`, 목록만 보기 `tar tvf`. 실무에서 자주 쓰진 않고, 로컬 이미지 내용 확인용.
- **이미지 내부 뜯어보기**: tar 풀면 `manifest.json`(→ `jq`로 예쁘게 출력), `layers`가 한 줄씩 나열 = Dockerfile 명령 한 줄씩과 대응. `docker history`로 레이어(CMD 등)를 위→아래로 확인.
- **빌드 흐름(스프링 연계)**: 스프링 부트에서 Gradle wrapper 빌드 옵션으로 `.jar` 생성 → 빌드마다 새 jar → 그 jar를 COPY로 이미지에 넣음(코드 바뀌면 해당 레이어부터 재생성).
- **레지스트리 push(실습)**: 이미지에 태깅 후 push. 각자 고유번호(이니셜 등)를 붙여 자기 이미지를 구분해서 push.
- **예고**: 모레부터 Kubernetes(Pod, 자원 request/limit, CNI/CSI, EKS 등)로 이어짐.

## 예시

- **VM OS 선택** — 어떤 VM은 Windows, 어떤 VM은 Ubuntu/RedHat(VM의 장점).
- **호스트 8080 → 컨테이너 80** — 포트 포워딩/터널링으로 외부 요청을 내부로 전달.
- **통신사 야간 배포** — 큰 앱을 정해진 날 밤새 배포하던 방식 → MSA·컨테이너로 개별·빠른 배포로 전환.
- **SKT(AWS/ECR) vs 계열사(Azure DevOps)** — 레지스트리·CI/CD가 회사마다 제각각.

## 헷갈리는 점·질문

- VM vs 컨테이너 차이 — 핵심은 Guest OS 유무(컨테이너는 호스트 커널 공유라 가벼움).
- 이미지 vs 컨테이너 — 이미지는 불변 읽기 전용 템플릿, 컨테이너는 그 위에 쓰기 레이어를 얹어 실행되는 임시 인스턴스.
- 레이어가 왜 쌓이나 — Dockerfile 한 줄 = 레이어 한 장, 캐시 재사용을 위해 잘 안 바뀌는 것(베이스)을 아래에 둠.
- 컨테이너 임시성 ↔ 볼륨 — 컨테이너가 죽으면 데이터가 날아가므로 볼륨으로 영속성 확보.
- request vs limit — 자원 최소 보장 vs 최대 상한.
- 레지스트리 선택 — Docker Hub / Harbor / ECR 중 뭘? 회사·비용·환경에 따라 다름(케바케).

## 한 줄 요약

> 컨테이너는 Guest OS 없이 호스트 커널을 공유해 VM보다 가볍고, 이미지는 Dockerfile 한 줄 = 레이어 한 장의 불변 읽기 전용 층으로 쌓이며, 임시적인 컨테이너의 데이터는 볼륨으로 지키고 레지스트리로 push해 배포로 이어진다 — 이것을 유기적으로 관리하려 다음에 Kubernetes를 배운다.
